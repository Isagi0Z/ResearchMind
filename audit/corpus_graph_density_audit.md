# Corpus Graph Density Audit (M3-AUDIT-1)

**Date:** 2026-06-11
**Corpus:** 8 papers (Attention, BERT, ResNet, U-Net, Adam, BatchNorm, Dropout, GAN)
**Graph:** 57 nodes, 1,913 edges, 0.60 density

---

## Executive Summary

The 8-paper evaluation corpus produces a graph with **1,913 edges** and **density 0.60**, of which **23.78% (455 edges) are semantic duplicates** — identical `(source, target, relation_type)` with different edge IDs. The dominant contributor is **Stage 5 entity co-occurrence** (1,176 edges, 61.47%), driven by BERT's 49 entity clusters producing C(49,2)=1,176 COMPARES_WITH pairs. Removing all duplicates would yield **1,458 unique edges** and **density 0.46**.

**Critical bug found:** Stage 8 deduplication is a **no-op** because it keys on `edge_id` (random UUID), not on `(source, target, relation_type)`. No two edges ever share the same edge_id.

## 3. Finding: Stage 5 Entity Co-Occurrence Dominance

**Classification: EXPECTED DESIGN (with caveat)**

Stage 5 generates `C(k, 2)` COMPARES_WITH edges for each document's resolved entity clusters. The cross-document `seen_pairs` set prevents duplicates when the same pair appears in multiple docs.

| Document                                  | Entities | Clusters (k) | Pairs C(k,2) |
|-------------------------------------------|----------|--------------|--------------|
| BERT: Pre-training of Deep Bidirectional  | 180      | 49           | 1,176        |
| Dropout: A Simple Way to Prevent Neural   | 119      | 41           | 820          |
| Deep Residual Learning for Image Recog.   | 106      | 36           | 630          |
| Batch Normalization: Accelerating Deep    | 66       | 25           | 300          |
| ADAM: A METHOD FOR STOCHASTIC OPTIMIZATI  | 53       | 22           | 231          |
| U-Net: Convolutional Network              | 24       | 12           | 66           |
| Attention Is All You Need                 | 36       | 16           | 120          |
| Generative Adversarial Nets               | 31       | 15           | 105          |
| **Total (raw)**                           | 615      | —             | **3,448**    |
| **After dedup (unique)**                  |          | 49           | **1,176**    |

**Observation:** BERT's 49 clusters alone produce 1,176 pairs, which equals the total after dedup. This means every pair from other documents was already generated by BERT — a consequence of BERT having the most diverse entity set that subsumes all others. The `seen_pairs` dedup saves 2,272 redundant pairs.

**Impact on density:** If Stage 5 were removed, density drops from 0.60 to 0.23. The O(k²) scaling means documents with many clusters dominate the edge budget.

**Caveat:** The Stage 5 loop is:

```python
for i in range(k):
    for j in range(i + 1, k):
        pair = (clusters[i], clusters[j])
        if pair not in seen_pairs:
            seen_pairs.add(pair)
            # create COMPARES_WITH edge
```

This generates edges even when two entities have no meaningful semantic relationship — any two entities co-occurring in the same document produce a COMPARES_WITH edge. This is intentional (maximal connectivity for graph traversal) but inflates density.

## 4. BUG: Stage 8 Dedup is a No-Op

**Classification: BUG**

**Evidence:** All 1,913 edges have unique edge_ids (zero collisions).

**Root cause:** `_stage_8_deduplicate` keys its `seen` dict by `edge_id`:

```python
def _stage_8_deduplicate(self, edges):
    seen = {}
    for e in edges:
        seen[e.edge_id] = e  # last wins if ID collision
    return list(seen.values())
```

Every stage generates edge_ids using `uuid.uuid4().hex[:12]`, producing random 12-character hex strings. No two edges ever share the same edge_id regardless of whether they have the same `(source, target, relation_type)`.

**Fix should be:** Key on `(e.source_id, e.target_id, e.relation_type)`:

```python
def _stage_8_deduplicate(self, edges):
    seen = {}
    for e in edges:
        sig = (e.source_id, e.target_id, e.relation_type)
        if sig not in seen:  # keep first occurrence
            seen[sig] = e
    return list(seen.values())
```

**Impact if fixed:** Removes 455 edges (23.78%), reduces density from 0.60 to 0.46. All removed edges are from Stage 3 (399 duplicates) and Stage 4 (56 duplicates).

## 5. Finding: Stage 3 Duplicate EXTENDS Edges

**Classification: QUESTIONABLE — design trade-off**

**Evidence:** Stage 3 creates one edge per entity, not per unique `(doc, cluster)` pair:

| Metric                       | Value    |
|------------------------------|----------|
| Total Stage 3 edges          | 615      |
| Unique (doc, cluster, EXTENDS) | 216    |
| Duplicate groups             | 196      |
| Duplicate edges              | 399 (65%) |
| Worst case                   | GAN doc → ec_4d50c0396dea (Markov): **5 edges** |

**Root cause:** In `_stage_3_document_entity_edges`, the code iterates over ALL entities in a document and creates one EXTENDS edge per entity that resolves to an entity cluster. If a document has 5 different entity IDs that all resolve to the same cluster "Markov", you get 5 EXTENDS edges from the same doc to the same cluster.

```python
for entity_id, cluster_id in self.eid_to_cluster.items():
    doc_id = self._get_doc_for_entity(entity_id)
    if doc_id:
        edges.append(CorpusEdge(
            source_id=doc_id,
            target_id=cluster_id,
            relation_type=RelationType.EXTENDS,
            edge_id=f"de_{uuid.uuid4().hex[:12]}",
            ...
        ))
```

**Trade-off:**
- **Defense (current design):** Each entity ID represents a distinct occurrence in the text. Multiple occurrences of "Markov" in GAN are different evidence instances. Keeping separate edges preserves evidence traceability.
- **Critique:** For graph analysis (density, centrality), multiple edges between the same `(doc, cluster)` inflate metrics. A better design would create **one edge with an edge count attribute** or dedup at the graph level.

**Impact:** If Stage 3 were deduped to unique `(doc, cluster, rel)`, edges drop from 615 to 216 (399 removed). Total graph goes from 1,913 to 1,514, density from 0.60 to 0.47.

## 6. Finding: Stage 4 DocumentRelation Duplicates

**Classification: BUG (same root cause — lack of semantic dedup)**

**Evidence:** Stage 4 creates 122 edges but only 66 unique `(doc, doc, relation_type)` signatures — 56 duplicates.

**Root cause:** `DocumentRelationEngine` creates one `DocumentRelation` object per pair of documents that share an entity. If two documents share multiple entities, multiple DocumentRelation objects are created, each generating a separate edge. Stage 8 should remove these but fails because it keys on edge_id.

**Impact:** 56 redundant edges inflate doc-doc density. Fixing Stage 8 dedup would remove these.

## 10. Findings Summary

| # | Finding | Classification | Impact |
|---|---------|---------------|--------|
| 1 | **Stage 8 dedup keys on edge_id instead of (src, tgt, rel_type)** | **BUG** | 455 duplicate edges not removed; density 0.60 vs corrected 0.46 |
| 2 | **Stage 3 creates one EXTENDS edge per entity, not per (doc, cluster)** | QUESTIONABLE | 399/615 Stage 3 edges are duplicates (65%); inflates doc degree by ~3x |
| 3 | **Stage 5 O(k²) co-occurrence explosion** | EXPECTED DESIGN | 1,176 edges from BERT's 49 clusters; dominates 61% of graph budget |
| 4 | **Stage 4 DocumentRelation creates duplicate edges** | **BUG** (subcase of #1) | 56/122 Stage 4 edges are duplicates |
| 5 | **Density formula is mathematically correct** | EXPECTED DESIGN | Matches manual calculation exactly |
| 6 | **Density cap at 1.0 prevents overflow from multigraph** | EXPECTED DESIGN | Necessary for directed multigraphs |
| 7 | **Cross-doc dedup in Stage 5 (seen_pairs) works correctly** | EXPECTED DESIGN | 2,272 redundant pairs eliminated |
| 8 | **DOC density exceeds 1.0 without cap** | QUESTIONABLE | Multigraph + duplicates push doc-only density to 2.18 |

### Recommendations

1. **Fix Stage 8 dedup** (HIGH priority) — Change key from `edge_id` to `(source_id, target_id, relation_type)`. This immediately removes 455 duplicate edges and drops density to 0.46.

2. **Consider Stage 3 per-entity vs per-cluster design** (MEDIUM priority) — If the data model supports edge attributes, merge duplicate (doc, cluster, EXTENDS) edges with a `count` attribute tracking entity occurrences. Alternatively, keep current behavior but document that edge multiplicity reflects entity occurrence frequency.

3. **Consider Stage 5 entity-filtering threshold** (LOW priority) — Entities with very low confidence or ambiguous resolution could be filtered before co-occurrence generation to reduce O(k²) noise. This is a semantic trade-off (recall vs precision).
